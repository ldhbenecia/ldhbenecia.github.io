## ADR-1. 프레임워크와 호스팅

### 선택지

#### A. Next.js 정적 export (GitHub Pages)
| 장점 | 단점 |
| --- | --- |
| 기존 배포 워크플로우 그대로, 서버 비용 0 | 이미지 최적화·서버 기능 없음 |

#### B. 순수 HTML/CSS
| 장점 | 단점 |
| --- | --- |
| 의존성 없음 | 콘텐츠와 마크업이 섞이고 컴포넌트 재사용이 어려움 |

### 결정: **A**

### 근거
1. 개인 포트폴리오에 서버가 필요한 기능이 없다
2. 콘텐츠를 데이터로 분리하고 섹션을 컴포넌트로 나누는 구조가 갱신에 유리하다
3. Tailwind·Radix·shadcn 등 Figma 생성 코드가 남긴 의존성은 쓰지 않으므로 제거한다

## ADR-2. 팔레트

### 선택지

#### A. 로즈 그레이 + 초록 (taste-skill 추첨안)
| 장점 | 단점 |
| --- | --- |
| 개성 있음 | 소유자 취향(검정·짙은 파랑)과 맞지 않음 |

#### B. 블루블랙 + 콘플라워 블루, 수면 필드
| 장점 | 단점 |
| --- | --- |
| 취향 방향 | 시안 검토에서 "너무 밝다"로 기각 |

#### C. 검정 + 짙은 네이비, 액센트 최소
| 장점 | 단점 |
| --- | --- |
| 취향과 일치, 화면 캡처가 색을 맡음 | 단조로워질 위험 — 인터랙션으로 보완 |

### 결정: **C**

### 근거
1. 소유자가 검정과 짙은 파랑 계열을 선호하고 B를 밝다고 판단함
2. 밝은 면(필드)을 두지 않고 표면은 네이비 톤 단계로만 구분한다
3. 액센트는 링크, 개선 후 수치, 현재 위치, 인터랙션 반응에만 쓴다

## ADR-3. 서체

### 선택지

#### A. Red Hat Display 900 대문자 + Pretendard
| 장점 | 단점 |
| --- | --- |
| 강한 포스터 느낌 | 시안 검토에서 "폰트가 이상하다"로 기각 |

#### B. Geist + Pretendard
| 장점 | 단점 |
| --- | --- |
| 기술 제품 톤, 숫자가 단정함 | 한글은 Pretendard로 대체되어 두 서체가 섞임 |

### 결정: **B**

### 근거
1. 라틴·숫자는 Geist가, 한글은 폴백 순서상 Pretendard가 맡는다
2. 굵기는 제목 600~700, 본문 400. 900은 쓰지 않는다
3. 큰 글씨일수록 자간을 좁힌다 (-0.025em ~ -0.05em)

## ADR-4. 히어로

### 선택지

#### A. 이름을 화면 가득 (수면선 헤드라인)
| 장점 | 단점 |
| --- | --- |
| 인상이 강함 | 시안 검토에서 어색하다는 평가로 기각 |

#### B. 인프라 토폴로지 캔버스 + 인사말
| 장점 | 단점 |
| --- | --- |
| 백엔드 → SRE 방향을 그림으로 보여 주고 커서에 반응 | 캔버스 성능·접근성 처리 필요 |

### 결정: **B**

### 근거
1. 노드와 연결은 실제 클러스터·프로젝트 구성만 옮긴다 (`content/topology.ts`). 지어낸 연결은 넣지 않는다
2. 화면 밖이거나 탭이 숨겨지면 그리지 않고, reduced-motion 이면 정지 프레임만 그린다
3. 제목은 인사말("안녕하세요, 임동혁입니다.")로 둔다

## ADR-5. 콘텐츠와 스타일 구조

### 결정: **콘텐츠는 `content/*.ts`, 색·서체·모션은 `app/tokens.css`, 섹션 스타일은 같은 이름의 `.module.css`**

### 근거
1. 이력 갱신이 화면 코드를 건드리지 않게 한다
2. 섹션 CSS는 토큰만 참조한다. 새 색이 필요하면 토큰을 먼저 추가한다

---

## ADR-6. 제품 화면 표현

### 결정: **모든 화면 캡처를 맥 창 모양으로 통일**

### 근거
1. Cairn·Mono Mail 원본은 투명 배경에 창 테두리·그림자가 들어 있다 (`framed: true`). JPEG로 바꾸지 않는다
2. 테두리가 없는 캡처는 화면에서 같은 모양의 창(신호등 바, 10px 모서리)을 씌운다
3. 개인정보(학교 메일, 성적 알림 등)가 보이는 캡처는 쓰지 않는다
4. 거래소 약관상 orbit 은 가상 데이터 화면만 쓰고 그 사실을 캡션으로 밝힌다

## ADR-7. 하우스 룰

### 결정

- 제목(h1~h3)은 모든 폭에서 두 줄 이하
- 제목 위 작은 라벨(eyebrow)·알약 배지·아이콘 카드 그리드를 쓰지 않는다
- 그라디언트는 히어로 아래쪽 가독성용 스크림 하나만 허용
- 정지 상태의 그림자는 창 모양 화면 캡처에만
- 숫자는 tabular figures
- 모든 모션은 transform·opacity·clip-path 만 쓰고 `prefers-reduced-motion` 대체 상태를 둔다. 스크립트가 없어도 내용은 보인다
- 수치는 이력서·레포 README·실측 기록에 근거가 있는 것만

### 근거
1. taste-skill 하우스 룰을 따르되, 소유자가 원한 인터랙션(토폴로지, 커서 미리보기, 쿼리 재생)은 예외로 둔다

## ADR-8. 라이트 모드

### 선택지

#### A. 다크 전용
| 장점 | 단점 |
| --- | --- |
| 유지할 팔레트가 하나 | 밝은 화면을 선호하는 방문자 배려 없음 |

#### B. 시스템 설정 + 토글, 즉시 전환
| 장점 | 단점 |
| --- | --- |
| 구현 단순 | 화면 전체가 순간 번쩍임 |

#### C. 시스템 설정 + 토글, 원형 전환 애니메이션
| 장점 | 단점 |
| --- | --- |
| 전환 자체가 인터랙션이 됨 | View Transition 미지원 브라우저 대비 필요 |

### 결정: **C**

### 근거
1. 소유자가 "딱 바뀌지 않고 애니메이션이 있는" 전환을 원함
2. 저장한 선택이 없으면 시스템 설정을 따르고, 페인트 전 스크립트로 테마를 정해 깜빡임이 없게 함
3. 토큰 이름은 그대로 두고 `:root[data-theme='light']` 에서 값만 바꿈. 캔버스 색도 토큰(`--topo-*`)에서 읽음
4. 미지원 브라우저는 색 페이드, reduced-motion 은 즉시 전환

## ADR-9. 연락과 UI 문구

### 결정: **연락은 GitHub·Blog·LinkedIn 링크만, 큰 글씨 없이. 내비·버튼·상태 같은 UI 문구는 영어**

### 근거
1. 메일 보내기 버튼과 화면 폭을 채우는 큰 이메일·링크 글씨는 시안 검토에서 기각됨
2. 본문은 한국어로 두되, UI 문구는 짧고 일관되게 영어로 통일
3. 'SRE·DevOps 로 넘어가는 중' 같은 전환 멘트는 화면에 쓰지 않음
